## Рекомендации по повышению тестируемости приложения для автоматизированных E2E сценариев

### TL/DR

- Все **компоненты** на каждой **странице** приложения должны быть помечены атрибутом `data-testid`
- Значение `data-testid` должны быть уникальными в пределах **страницы** 
- Если **компонент** включает в себя несколько **дочерних компонентов**, дочерние компоненты должны обладать уникальным
  значением `data-testid` в пределах **родительского
  компонента**.

Пример:

1. Некая страница содержит экземпляр компонент `EntityObjectsTable`, реализующий функционал таблицы => каждый экземпляр
   этого компонента должен обладать уникальным `data-testid` в рамках страницы.
    ~~~typscript  
    <EntityObjectsTable 
              data-testid={TestIds.OrdersTable} // Уникальный data-testid для конкретного компонента на странице, к примеру datatest-id='orders-table'
              entityType={entityType}
              listQuery={listQuery}
              entitySearchField={<EntitySearchField entityType={entityType} listQuery={listQuery} />}
              buttonContent={ ... }
              menuItems = { ... }
    />
    ~~~
2. Внутри себя компонент `EntityObjectsTable` использует компонент `EntitySearchField`, реализующий поле поиска по
   таблице => каждый экземпляр компонента `EntitySearchField` должен иметь уникальный `data-testid` в рамках
   компонента `EntityObjectsTable`
   ```typescipt
   export const EntitySearchField: FC<IEntitySearchField> = ({
     entityType,
     listQuery,
     dataTestId = TestIds.TableSearchBar, // Уникальный data-testid для всех компонентов "поиска по таблице", к примеру datatest-id='table-searchbar'
   }) => {
     return < ... >
     );
   };
   ```

### Предпосылки и проектный смысл

E2E сценарии, автоматизирующие тестирование пользовательского интерфейса, чаще всего взаимодействуют с приложением с
помощью инструментов так, или иначе, реализующих протокол WebDriver. С практической точки зрения это означает, что
тесты работают с приложением как с черным ящиком, контрактом (или, если угодно, API) которого выступает DOM дерево
страницы. Соответственно, поддержание этого контракта в _единой_ и _стабильной_ форме позволяет существенно снизить
затраты на поддержку существующих автотестов при изменениях в функционале и высвобождает ресурсы для расширения
покрытия, и, как следствие, повышает уровень качества приложения.

### Data-Testid

Самым эффективным с точки зрения соотношения затрат к выгоде способом составления такого контракта является введение
отдельного html атрибута (назовём его `data-testid`) для всех **значимых** элементов приложения, позволяющего однозначно
их
идентифицировать. Под "значимым элементом" понимается любой элемент страницы который:

1. **видим** и предоставляет пользователю **необходимую** информацию для прохождения пользовательского пути (в основном
   метки и
   иконки) и при этом не несёт сугубо декоративный характер (различные спейсеры, рекламные банеры и т.д.)
2. **видим** и предоставляет пользователю возможность **взаимодействовать** с функционалом приложения (всевозможные
   кнопки и
   поля ввода в самом широком смысле)
3. **невидим**, но является корневым контейнером **составного** элемента

### Простые элементы DOM

В случае с простыми элементами, т.е. состоящими из одного элемента, с которым происходит взаимодействие (кнопка, поле и
т.д.)
применимы пункты **1.** и **2.** из списка выше. Для того чтобы построить локатор, однозначно идентифицирующий такой
элемент его `data-testid` должен быть уникальным в рамках всей страницы в целом. К примеру:

~~~xpath
//*[@data-testid='create-order-btn']
~~~

### Составные элементы DOM

В случае с составными элементами, т.е. состоящими из множества элементов, с которым происходит взаимодействие (таблицы,
выпадающие списки, календари
ввода и т.д.) `data-testid` у корневого элемента должен быть уникальным в рамках всей страницы, а `data-testid` у его
дочерних элементов в свою очередь уникальным в рамках родительского контейнера.

К примеру, представим, что на странице присутствует таблицы `orders` и `clients`. Тогда поля поиска этих таблиц должны
быть находимы с помощью следующих локаторов:

~~~xpath
//*[@data-testid='orders-table']//*[@data-testid='table-search-field']
~~~

и

~~~xpath
//*[@data-testid='clients-table']//*[@data-testid='table-search-field']
~~~

соответственно, где `clients-table` и `orders-table` - уникальные атрибуты корневого элемента таблицы,
а `table-search-field` - уникальный атрибут поля поиска, в пределах тела каждой отдельной таблицы.

Такой подход позволит переиспользовать как сами составные элементы в рамках front-end разработки, так и оснастку для
их тестирования в библиотеках автотестов.
